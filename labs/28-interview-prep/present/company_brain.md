# Company Brain: הצגה בחמש דקות

> קובץ התחלה. מה שכבר ידוע מהקורס כתוב; כל מה שבסוגריים מרובעים ממלאים אחרי שמודדים בפרויקט הסיום (F1). אל תשאיר מספר שלא מדדת.

## 1. הבעיה והמשתמש
עובדי Acme מבזבזים זמן על שאלות שהתשובה עליהן כתובה במסמכי החברה (מדיניות HR, נהלי IT, מדיניות גישה ל-SaaS), ובקשות גישה למערכות עוברות במייל ומחכות [X שעות] לניתוב ידני. הצלחה: תשובה עם מקור תוך [X] שניות, ובקשת גישה שמנותבת נכון ל-auto_approve, needs_manager או needs_security, עם אישור אנושי איפה שהמדיניות דורשת.

## 2. ארכיטקטורה
- ingestion של מסמכי Acme: chunking לפי סעיפים, embeddings, ו-[pgvector או אחר] עם metadata של הרשאות.
- שאלות: hybrid search (BM25 ו-embeddings, RRF), reranker, ותשובה עם ציטוטים שנבדקים בקוד.
- בקשות גישה: חילוץ עם structured output (AccessRequest מ-llmkit.structured), ניתוב בכללים דטרמיניסטיים לפי המדיניות, ו-workflow עם checkpoint ושער אישור אנושי.
- שרת MCP שחושף את הכלים, ניטור עם traces, ופריסה ב-AWS.

## 3. החלטה אחת עם trade-off
workflow קבוע ולא סוכן חופשי לבקשות הגישה: הסדר ידוע והסיכון גבוה, ולכן העדפתי צפיות, בדיקות לכל שלב ושער אישור מובטח, על חשבון גמישות. [אם בפרויקט בחרת אחרת, כתוב את ההחלטה שלך ואת הנימוק.]

## 4. מדידה
- golden set: [N] שאלות עם תשובה ומקור, ו-24 בקשות גישה עם המסלול הנכון (מהמעבדה של שיעור 3, ועוד [N]).
- retrieval: recall@5 = [X]. תשובות: faithfulness = [X]% לפי שופט שכויל מול [N] תיוגים שלי.
- ניתוב בקשות: [X]% נכון, ו-[0] בקשות רגישות שאושרו אוטומטית.
- p95 latency = [X] שניות, עלות = [X] דולר לשאלה.

## 5. כשל אמיתי
דוגמה מהקורס שאפשר להשתמש בה: לפי התיעוד, pattern פשוט ב-JSON Schema נתמך ב-structured outputs של Claude, אבל בבדיקה חיה הבקשה החזירה 400 "Schema is too complex". בודדתי את זה עם סכמה מינימלית, ושיניתי את llmkit כך שאילוצים שהספק לא אוכף עוברים לתיאור ונאכפים ב-Pydantic.
